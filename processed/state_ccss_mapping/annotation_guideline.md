# Annotation Guideline: Mapping state math standards to CCSS (K–5)

This guideline tells an annotator how to map one state's K–5 mathematics standards onto the Common Core State Standards for Mathematics (CCSS), K–5. It was established by three annotators while jointly adjudicating a complete mapping of Georgia's K–5 standards, and it is written to apply to any state.

Annotate alone, using only the provided materials (the state and CCSS standards and this guideline). Do not consult other mappings, annotators, or model output.

## 1. Task Definition

For each state standard, record:

- Which CCSS code it corresponds to: zero, one or more
- How it relates to each: one of seven relationship types per state standard, CCSS code pair

A “correspondence” means the two standards require the same learning of students. It does not mean they are on the same topic. Definition of “same learning” involves action (what students do), the content (the math) and the bounds (number ranges, cases).

Annotate content standards only. Mathematical Practice standards like Georgia K.MP.1–K.MP.8 at each grade are not annotated because they correspond to the CCSS Standards for Mathematical Practice, which are not in the K–5 content list.

## 2. Units

**State Units:**
Annotate each standard at its lowest level. The smallest unit the state numbers or letters (e.g. Georgia K.NR.1.1; a lettered part of a Virginia standard, 3.MG.2 a).

**CCSS Units:**
Cite leaf codes. A CCSS standard’s lettered parts where it has them (e.g. 3.MD.7a, 3.MD.7b), otherwise the standard itself (e.g. 3.MD.6). Never cite a parent standard that has lettered parts (e.g. 3.MD.7).

## 3. Reading a standard

### The standard’s own text sets the requirement

What a standard requires is what its own text says, read in its context. The parent standard, cluster and domain tell you what the text is about and how to understand it. This context and any additional information (examples, strategies, limits) are used to interpret that text; what a term means, which numbers or representations are intended, what is out of scope at that grade. They should never add a requirement the text doesn’t state.

e.g.) Georgia’s additional guidance description for 3.NR.1.2 "compare multi-digit numbers up to 10,000…") mentions dot plots and bar graphs as one setting for comparing numbers. The standard's text asks only to compare numbers (Use place value reasoning to compare multi-digit numbers up to 10,000, using >, =, and < symbols to record the results of comparisons), so graphing is not part of its requirement.

### Identify each standard’s core requirement

Before comparing, identify each state and CCSS standard by:

- **Action:** what students must do (count, identify, compare, represent, compute, solve problems, explain, draw, create, measure…)
- **Content:** the mathematics the action applies to (e.g. fractions with the same numerator or denominator; area of rectangles).
- **Bounds:** limits on that content (number ranges, place values, number types, denominators, which cases).

A standard can have more than one requirement (e.g. "measure lengths … and show the data on a line plot"). List each separately.

## 4. Comparing standards

Comparison of a state standard with a CCSS code comes down to two questions.

- Do the two standards share a requirement?
- Which is inside which?

| Question | Tests | What the answer decides |
|---|---|---|
| Do the two standards share a requirement? | A, B | yes → the pair gets a row; no → no row |
| Which is inside which? | C, D | which differences count; a difference that counts means the standard that has it is not inside the other (the one without it may still be inside) |

### Do the two standards share a requirement? (A & B)

#### Test A : shared requirement, not shared topic

Two standards correspond only if they share a requirement. The same action on the same content (one whole requirement or part of it). Being about the same topic is not enough. Differences in bound don’t prevent a match; they decide which standard is inside which (Test D)

e.g. Identifying coins and their values (Georgia K.NR.1.4) and solving word problems with coins (CCSS 2.MD.8) share a topic, not a requirement. No match.

#### Test B: not every related code is a match

CCSS code do not correspond if it is:

- A same-topic code that asks for a different action (Test A)
- A prerequisite the state standard builds on but doesn’t itself state
- A base definition the state standard assumes but doesn't state (e.g. CCSS 3.MD.5a, "A square with side length 1 unit, called 'a unit square,' is said to have 'one square unit' of area…"). A state standard that uses the concept matches the CCSS code that uses it, not the definition
- a code two or more grades above the state standard, covered only with narrower bounds. An early, simpler version of later content.

### Which is inside which? (C & D)

When one standard has something the other doesn’t, the difference either matters or is ignored. When unsure whether a difference matters, treat it as ignored, and mark the row low confidence.

#### Test C: does a difference in what students do matter?

A difference matters only if it is a separate learning objective: something a teacher would plan, teach and assess as its own goal.

**Matters (the standard that has it is not inside the other) :**

- A different product or skill: making a line plot, drawing figures, solving word problems, a second operation, counting backward as well as forward, measuring elapsed time…
- fluency ("fluently", "demonstrating fluency") : performing a task fluently and performing the same task without a fluency requirement are treated as different.
- a different or wider number range, number type, place value or set of cases (Test D)

**Ignored :**

- Wording, phrasing, emphasis
- other words about how the action is done, such as "mentally" or a specific procedure ("using the standard algorithm"): unlike fluency, neither document defines these as a separate expectation
- methods, tools or representations given as examples ("e.g.", "such as", "for example", "using objects or drawings")
- a demand attached to the main task: recording the result with symbols, justifying or explaining the result, estimating alongside measuring or telling time, using a model to show it. When such an action is a standard's whole task (e.g. CCSS 2.MD.3, "Estimate lengths using units of inches, feet, centimeters, and meters"), consider it as that standard's main action.
- productive forms of the same skill on the same content (identifying written numerals vs. writing them, when both standards require representing quantities with numerals)
- ordinary components of the task (finding the value of a group of coins as part of solving money problems);
- a general setting ("in authentic problems", "in real-world contexts"), unless the other standard's requirement is specifically problem solving.

*Why explaining and justifying are ignored:* the question is whether two standards target the same learning, not how that learning is shown. Explaining and justifying are expected across all standards (e.g. CCSS Mathematical Practice 3).

#### Test D: a difference in bounds always matters

A different number range (to 20 vs. to 100), number type (whole numbers vs. fractions vs. decimals), place value (to hundredths vs. to any place), denominators, number of digits, number of steps, or set of cases. The standard with the narrower bounds is inside the other (e.g. rounding to hundredths is inside rounding to any place); if each is wider in a different way, neither is inside the other.

## 5. Relationship types

Each row of the annotation is one state standard and CCSS code pair. EAch row gets one of seven labels describing that pair. A state standard citing several CCSS codes will have several rows and they may carry different labels. This section elaborates on what each label means.

The labels are determined on one question: which standard is inside which? One standard is inside another when everything it requires (objective and bound) is also required by the other. Differences that are not separate objectives, such as a missing "explain why", or in grades between standards, is not a disagreement in requirements.

| type | meaning | Which is inside which? | Nuance |
|---|---|---|---|
| exact | same standard, at any grade | each inside the other | a state standard has at most one exact row, and a CCSS code is exact with at most one state standard. If a second state standard is also the same as a CCSS code you already marked exact, re-examine both. Usually each covers a separate part of it (split), or one of them differs in scope. |
| split | one CCSS code, spread over several state standards | the state standard is inside the code | the state standards that cover parts of the code together make up all of the code, and this row's state standard is needed for that |
| state_subset | the state asks for less than the code | the state standard is inside the code | the state standards that cover parts of the code do not make up all of the code; or they do, but this row's state standard is not needed for that |
| merge | one state standard, several CCSS codes | the code is inside the state standard | the CCSS codes that cover parts of the state standard together make up all of the state standard, and this row's code is needed for that |
| state_superset | the state standard has the code’s requirement and more | the code is inside the state standard | the CCSS codes that cover parts of the state standard do not make up all of the state standard; or they do, but this row's code is not needed for that |
| overlap | they share some requirements, and each also has a requirement the other lacks | neither | The row still counts as a piece on both sides. It helps the state standards that cover parts of the code make up the code, and the CCSS codes that cover parts of the state standard make up the state standard |
| none | no CCSS counterpart | - | no CCSS K–5 code shares any of the state standard's requirements; one row, with no code |

**Pieces :** A code’s pieces are the state standards that cover part of it: its split, state_subset and overlap rows. A state standard’s pieces are the codes that cover part of it: its merge, state_superset, and overlap rows. An overlap row keeps its own label but counts as a piece on both sides at once, like a split piece for the code and a merge piece for the state standard: it can help the other rows make up a whole (split and merge).

**Merge and split are mirrors of each other :** Both ask whether the pieces make up a whole, from opposite sides:

| | One CCSS code, several state standards | One state standard, several CCSS codes |
|---|---|---|
| Pieces makes up whole | split on each state standard inside the code | merge on each code inside state standard |
| Pieces do not make up whole | state_subset | state_superset |
| Piece is neither inside nor contains | overlap | overlap |

**Potential Patterns :** Here, A, B, C and X are CCSS codes and R, S, T, U and V are state standards at their smallest unit. Lowercase letters are parts of a standard (a1 and a2 are the two parts of A), they are NOT a sub-standard, just different requirements of the lowest level standard. “Y” is a part that no CCSS code requires.

| # | Pattern | Standards | Rows |
|---|---|---|---|
| 1 | Split | A = a1 + a2; S = a1; T = a2 | S-A split, T-A split: S and T together make up A |
| 2 | Split and a standard that isn’t needed | #1 plus R = smaller number version of a1 | S-A split, T-A split, R-A state_subset: A is whole without R |
| 3 | Merge | S = all of A + all of B | S-A merge, S-B merge: A and B together make up S |
| 4 | Merge and a code that isn’t needed | S = all of B + all of C; A is inside S, but B already covers A's part more fully. A + C does not cover S fully. | S-B merge, S-C merge, S-A state_superset: S is made up without A. |
| 5 | Superset | S = all of A + y | S-A state_superset: y is covered by no code |
| 6 | Overlap pieces completing two splits | A = a1 + a2; B = b1 + b2; S = a1 + b1; T = a2; U = b2 | S-A overlap, S-B overlap (S has another part each code lacks and each code has another part S lacks); T-A split (T and the overlap piece make up A); U-B split (U and S overlap make up B) |
| 7 | An overlap piece completing a merge | X = x1 + x2; S = all of X; T = all of A + x1 | S-X exact; T-X overlap (T has A, which X lacks; X has x2, which T lacks); T-A merge (A and the overlap piece X make up T). X has different labels on different rows. |
| 8 | Overlap that isn't needed in other relationships | V = all of A; S = a1 + y | V-A exact; S-A overlap (S has y, which A lacks; A has a2, which S lacks) |

## 6. Decision Procedure

Steps 1-4 find the codes, one row each. Steps 5-6 label each row. Record the step at which you decided in the row’s rationale.

### Step 1. Identify

Identify the state standard’s core requirement: action, content, bounds.

### Step 2. Search

Search the whole CCSS list of all domains and grades starting at the state standard's own grade and corresponding domain. States organize content differently (e.g. Georgia puts area under geometry, CCSS under Measurement and Data). Search in both directions:

- **Every part of the state standard:** look for a code that requires each part. Don't stop at the first match; a state standard often combines several codes from any domain or grade. A part that no code requires stays uncovered.
- **Every part of the code:** for a code the state standard covers only partly, search the state’s standards for the parts it doesn’t cover. These are its possible split partners.

### Step 3. Keep the codes that share a requirement

Keep a candidate code only if the state standard states one of its requirements, whole or a part (Test A). A shared detail, example or topic is not enough. Drop prerequisites, assumed definitions, same-topic codes with a different action, and later codes the standard only introduces (Test B).

For each part of the state standard, cite the code that matches it most closely. A code is cited whenever it is the closest match for some part, even if it doesn't help make up a whole (e.g. an overlap or state_subset row).

### Step 4. Count the codes kept

- 0 → one row labeled none. Stop.
- 1 or more → one row per code. Label each row with steps 5–6.

### Step 5. Which is inside which?

Compare the state standard with the row's code (Tests C & D):

| Comparison | Label |
|---|---|
| Each is inside the other | exact |
| Neither is inside the other | overlap (fill split_with and merge_with) |
| The state standard is inside the code | Step 6A |
| The code is inside the state standard | Step 6B |

Section 5’s pattern list shows how labels combine across rows.

### Step 6. Do the pieces make up the whole?

**A. The state standard is inside the code**

Of all the state standards that cover part of the code, including overlap rows, which together make up all of it?

| This row’s state standard is.. | Label |
|---|---|
| needed with the others to cover all of the code’s parts | split |
| not needed because another standard already covers its part more fully, one standard covers the whole code, or no combination covers the full code | state_subset |

If two sets of standards each make up the code (e.g. in grade 3 and again, more fully, in grade 4), only the set with the fuller scope is split and the other standards are just state_subset. A part covered with somewhat narrower bounds (e.g. quarter hours rather than minutes) still counts, just note in rationale. When unsure whether this row’s state standard is needed, choose state_subset and mark the row low confidence.

**B. The code is inside the state standard**

Of all the codes that cover part of the state standard, including overlap rows, which together make up all of it?

| This row’s code is.. | Label |
|---|---|
| needed with the others to cover all of the state standard’s parts | merge |
| not needed because another code already covers its part more fully, one code covers the whole standard, or no combination covers the full standard | state_superset |

## 8. What to record

Ensure that per every state standard, CCSS code pair, there is one single recorded row. A state standard with several CCSS codes gets one row per code; a CCSS code shared by several state standards appears on each of their rows; a none standard gets one row with no code recorded.

| Field | What to enter |
|---|---|
| state_code | The state standard's code |
| ccss_code | One CCSS leaf code; empty for none |
| relationship | One of the seven types for this pair |
| split_with | On a split row, and on an overlap row that helps make up this row's code, enter the other state standards that make up this row's code with this row’s state standard. Otherwise empty. |
| merge_with | On a merge row, and on an overlap row that helps make up this row's state standard, enter the other CCSS codes that make up this row's state standard with this row’s code. Otherwise empty. |
| confidence | high: the guideline decides it clearly; medium: a judgment within a clear rule; low: you are unsure about the mapping |
| rationale | One or two sentences on the requirement matched, the decisive difference (if any), and the test or step that supported it (e.g. "Step 6, Test D: rounds to hundredths only, CCSS to any place"). |

A standard's rows may carry different labels, because each describes one pair. split_with and merge_with record which rows belong together, including the overlap rows that help make up a whole. An overlap row that helps on neither side (pattern 8 in section 5) leaves both empty; one that helps on both sides fills both.

| Georgia merge | 3.NR.4.4 | 3.NF.3a | merge | | 3.NF.3b |
| | 3.NR.4.4 | 3.NF.3b | merge | | 3.NF.3a |
| Georgia split | 3.MDR.5.2 | 3.MD.1 | split | 3.MDR.5.3 | |
| | 3.MDR.5.3 | 3.MD.1 | split | 3.MDR.5.2 | |
| Georgia superset | K.NR.2.1 | K.CC.1 | state_superset | | |
| Georgia none | K.NR.1.4 | | none | | |
| Pattern 6 (section 5): S is part of two splits, one per row | S | A | overlap | T | B |
| | S | B | overlap | U | A |
| | T | A | split | S | |
| | U | B | split | S | |
| Pattern 7 (section 5): an overlap piece completing a merge | S | X | exact | | |
| | T | X | overlap | | A |
| | T | A | merge | | X |

Before moving on, check:

- every split row has split_with filled, and every merge row has merge_with filled.
- the partners agree. If row T-A lists S in split-with, the row S-A lists T (likewise for merge_with).
- each split_with group, with this row's state standard, makes up all of the code and each merge_with group, with this row's code, makes up all of the state standard.
- a none standard has exactly one row with no code.
- no parent code with lettered parts is cited.
